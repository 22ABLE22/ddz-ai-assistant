# 自动识牌方案评估：能不能套用 cardRecorder 的布局？

**结论：技术上能跑通，但不建议直接套用。** 三个硬伤都在工程层面，不是「改改就行」。

---

## 一、cardRecorder 到底怎么做的（读源码得出）

仓库 `yangdayangda/cardRecorder`（★156），定位是**欢乐斗地主记牌器**。

| 环节 | 实现 | 关键代码 |
|---|---|---|
| 取屏 | `MediaProjection` + `VirtualDisplay` + `ImageReader` | `FloatingWindowService:208` |
| 悬浮层 | `TYPE_APPLICATION_OVERLAY` 悬浮窗显示记牌结果 | `FloatingWindowService:74` |
| 裁剪 | **硬编码矩形** `handCard` / `player1` / `player2` | `ImageUtils.cropBitmap` |
| 识别 | OpenCV `Imgproc.matchTemplate` + `TM_CCOEFF_NORMED` | `CardDetectionUtil:38` |
| 加速 | `pyrDown` 降采样一半后再匹配 | `CardDetectionUtil:33` |
| 模板 | 15 张点数图 × 2 种尺寸（手牌 80px / 出牌区 60px） | `CardDetectionUtil:95` |
| 阈值 | 0.85，重叠框去重 | `CardDetectionUtil:45` |
| 轮询 | 每 1.5 秒截一次，点数集合变了才更新 | README |

权限要求：`SYSTEM_ALERT_WINDOW`（悬浮窗）+ `FOREGROUND_SERVICE` + `mediaProjection` 前台服务类型。

**它只识别点数，不识别花色** —— 斗地主只按点数比大小，这个简化是对的。

## 二、三个硬伤

### 硬伤 1：裁剪区硬编码 → 换手机就废

作者自己在 README 里写明：

> 在某些尺寸的手机上面运行可能会出错（虽然程序做了不同屏幕的适配），
> 可以自行修改项目里面的出牌区域或者每一个点数的截图。
> 在手机屏幕为 3200x1440 和 2400x1080 上面运行是没有问题的。

也就是说：**只有两种分辨率实测可用**。换个手机、换个游戏界面布局、游戏改一次版，
裁剪坐标和模板图全部要重新标定。这不是「适配」，是「每个设备各做一份」。

### 硬伤 2：OpenCV 体积

当前 APK **32.97 MB**。OpenCV Android SDK 的 `libopencv_java4.so`：

| ABI | 体积 |
|---|---|
| arm64-v8a | ~15 MB |
| armeabi-v7a | ~11 MB |

只带 arm64 也要 **+15 MB → 约 48 MB**。而且本项目的既定约束是
「无第三方 Android 依赖、完全离线」，引入 OpenCV 直接破坏这条。

### 硬伤 3：定位变了

当前应用是**手动录入的复盘/训练工具**：你自己报牌，它给建议，不碰游戏进程。
加上录屏识牌之后，它变成**实时对局辅助**——对着正在进行的线上对局出主意。

这是两个不同的产品。前者是学习工具，后者是对局外挂。
要不要跨这条线是产品决策，不是技术决策，但必须明确说出来。

## 三、如果要做，推荐的做法（避开三个硬伤）

### 关键改进：不引 OpenCV，用纯 Java 模板匹配

OpenCV 在这里只用了两个函数：`pyrDown`（降采样）和 `matchTemplate`（归一化互相关）。
这两个都能用纯 Java 在 `int[]` 像素数组上实现，**约 150 行**，零依赖。

```
Bitmap → int[] ARGB → 灰度 → 降采样 → 归一化互相关 → 峰值定位
```

成本对比：

| 方案 | 依赖增量 | 实现量 | 可测性 |
|---|---|---|---|
| OpenCV | +15 MB | 直接调 API | 需真机 |
| **纯 Java** | **0** | ~150 行 | **JVM 可测** |

### 关键改进：ROI 不硬编码，让用户标定一次

首次使用时让用户**在截屏上框选**三个区域（我的手牌 / 上家出牌区 / 下家出牌区），
坐标存本地。这样：

- 任何分辨率都能用，不需要按机型写死
- 游戏改版后用户自己重框一次即可
- 模板也可以让用户从自己的截屏里裁 —— 彻底摆脱「模板图过时」

### 关键改进：识别结果**不直接生效**，先给人确认

```
截屏 → 识别 → 候选结果 → 界面高亮 → 用户点确认 → 录入
```

这样识别错一两个点也不会污染对局记录。比全自动安全，也比纯手动省事。

## 四、结论与建议

| 问题 | 答案 |
|---|---|
| cardRecorder 的方案能跑通吗 | 能，但它自己承认只有 2 种分辨率可用 |
| 能直接套用到本项目吗 | **不建议**。OpenCV +15MB、硬编码 ROI、定位变化 |
| 有更好的做法吗 | 有：**纯 Java 匹配 + 用户标定 ROI + 结果先确认** |
| 现在该做吗 | 建议先明确产品定位。若定位是「复盘工具」，保持手动录入即可 |

### 为什么建议先不动

当前应用已经有**点选录入**（`playPicker`），输入成本本来就不高。
自动识牌省下的是「点几下」的时间，换来的是：

- 一个约 300 行、强依赖具体机型与游戏版本的脆弱模块
- 每次游戏更新可能要重新标定
- 产品定位从「训练工具」滑向「对局辅助」

**投入产出比不划算**，除非自动识别本身就是产品的核心卖点。

## 五、如果确定要做，实施顺序

1. `TemplateMatcher.java` —— 纯 Java 归一化互相关，输入 `int[]` ARGB，JVM 可测
2. `RegionStore.java` —— 用户标定的 ROI 持久化
3. `ScreenCaptureService.java` —— `MediaProjection` + 悬浮窗，复用 cardRecorder 的骨架
4. 识别结果 → 确认弹层 → 录入
5. 用真机截图做回归：同一张图，识别结果必须逐点稳定

第 1 步是唯一可以脱离真机验证的部分，也是最能复用的一部分。
其余部分都需要真机 + 目标游戏的实测截图才能调准。
